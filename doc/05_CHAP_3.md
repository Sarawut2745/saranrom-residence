# บทที่ 3
# ขั้นตอนการดำเนินงาน

บทที่ 3 นำเสนอรายละเอียดขั้นตอนการดำเนินงานจัดทำโครงงานระบบบริหารจัดการหอพักและอพาร์ตเมนต์รายเดือน เดอะ สราญรมย์ เรสซิเดนซ์ ผ่านเว็บแอปพลิเคชัน (The Saranrom Residence) ตั้งแต่กระบวนการศึกษาและวิเคราะห์ความต้องการของระบบ การออกแบบเชิงฟังก์ชันด้วยแบบจำลองภาษามาตรฐาน UML การออกแบบโครงสร้างฐานข้อมูลเชิงสัมพันธ์และพจนานุกรมข้อมูล การออกแบบสถาปัตยกรรมระบบ การออกแบบส่วนติดต่อผู้ใช้งาน ตลอดจนแผนการพัฒนาและทดสอบระบบ เพื่อให้การพัฒนาระบบมีความสมบูรณ์ ถูกต้องตามหลักวิศวกรรมซอฟต์แวร์ และสามารถนำไปประยุกต์ใช้งานได้จริง โดยมีเนื้อหาแบ่งออกเป็น 6 หัวข้อหลัก ดังนี้

3.1 การศึกษาและวิเคราะห์ความต้องการของระบบ  
3.2 การวิเคราะห์และออกแบบระบบเชิงฟังก์ชันด้วยแผนภาพ UML  
3.3 การออกแบบฐานข้อมูลและพจนานุกรมข้อมูล  
3.4 การออกแบบสถาปัตยกรรมระบบและความปลอดภัย  
3.5 การออกแบบส่วนติดต่อผู้ใช้งาน  
3.6 แผนการพัฒนา การทดสอบ และการประเมินผลระบบ  

---

## 3.1 การศึกษาและวิเคราะห์ความต้องการของระบบ

### 3.1.1 ปัญหาของระบบเดิมและแนวทางการพัฒนาระบบใหม่
จากการลงพื้นที่ศึกษาและสัมภาษณ์ผู้บริหาร เจ้าหน้าที่นิติบุคคล และผู้พักอาศัยของหอพักเดอะ สราญรมย์ เรสซิเดนซ์ สามารถสรุปการวิเคราะห์ปัญหาและแนวทางแก้ไขเชิงระบบได้ดังแสดงในตารางที่ 3-1

**ตารางที่ 3-1** การวิเคราะห์ปัญหาของระบบเดิมและแนวทางแก้ไขในระบบใหม่

| กระบวนการทำงาน | ปัญหาของระบบเดิม (Manual / Paper-based) | แนวทางการแก้ไขในระบบ The Saranrom Residence |
| :--- | :--- | :--- |
| 1. การจดมิเตอร์น้ำ-ไฟ | จดด้วยมือลงสมุด คำนวณด้วยเครื่องคิดเลข เสี่ยงต่อการคลาดเคลื่อน ล่าช้า และเอกสารสูญหาย | บันทึกตัวเลขมิเตอร์ผ่านหน้าเว็บ ระบบคำนวณผลต่างหน่วยและคำนวณยอดเงินอัตโนมัติ |
| 2. การจัดทำใบแจ้งหนี้ | พิมพ์ใบแจ้งหนี้กระดาษและนำไปสอดตามประตู สิ้นเปลืองกระดาษ ผู้เช่าอาจไม่ได้รับ | ออกใบแจ้งหนี้ดิจิทัล ผู้เช่าเข้าดูผ่านพอร์ทัลส่วนตัวได้ทันที พร้อมดาวน์โหลดเป็น PDF |
| 3. การชำระเงินและตรวจสลิป | โอนเงินแล้วส่งสลิปผ่านแอปแชตส่วนตัว สลิปปะปนกับบทสนทนา ตรวจสอบยาก เสี่ยงสลิปซ้ำ | สร้าง QR Code PromptPay ตามยอดจริง บังคับแนบสลิปผ่านระบบ เจ้าหน้าที่ตรวจอนุมัติแบบรวมศูนย์ |
| 4. การแจ้งซ่อมแซม | แจ้งด้วยวาจาหรือข้อความแชต ข้อมูลตกหล่น ไม่ทราบระดับความด่วน ผู้เช่าตามสถานะไม่ได้ | ระบบ Ticket แจ้งซ่อม ระบุ 5 หมวดหมู่ ความเร่งด่วน แนบภาพถ่าย และติดตามสถานะได้แบบเรียลไทม์ |
| 5. การสื่อสารประชาสัมพันธ์ | ติดบอร์ดประชาสัมพันธ์ ผู้เช่าไม่ได้อ่าน พลาดข่าวสารและมาตรการสำคัญ | ระบบประกาศข่าวสารออนไลน์ ปักหมุดข่าวเร่งด่วน พร้อมเชื่อมโยงแจ้งเตือนผ่าน LINE Official |
| 6. การรายงานและสถิติ | บัญชีกระจายในสมุดและ Excel สรุปผลรายได้และอัตราครองเตียงล่าช้า ไม่เป็นปัจจุบัน | แดชบอร์ดสรุปรายรับ อัตราการเข้าพัก (Occupancy Rate) และประวัติการทำงาน (Audit Logs) แบบทันที |

### 3.1.2 ความต้องการเชิงหน้าที่ (Functional Requirements)
ระบบได้กำหนดข้อกำหนดเชิงหน้าที่ตามบทบาทผู้ใช้งาน (Role Model) ดังนี้:

1. **ความต้องการสำหรับผู้เยี่ยมชมทั่วไป (Visitor - FR-V)**:
   - FR-V01: ผู้เยี่ยมชมสามารถเข้าชมหน้าแรกเพื่อดูข้อมูลทั่วไป บรรยากาศโครงการ และสิ่งอำนวยความสะดวกได้
   - FR-V02: ผู้เยี่ยมชมสามารถดูรายการประเภทห้องพัก อัตราค่าเช่าเริ่มต้น ค่าน้ำ ค่าไฟ และสิ่งอำนวยความสะดวกประจำห้องได้
   - FR-V03: ผู้เยี่ยมชมสามารถดูข้อมูลที่ตั้ง แผนที่ และช่องทางการติดต่อ (โทรศัพท์, LINE Official Account) ได้
   - FR-V04: ผู้เยี่ยมชมสามารถกดเข้าสู่หน้าล็อกอินเข้าสู่ระบบได้

2. **ความต้องการร่วมของผู้ใช้งานระบบ (Base User - FR-B)**:
   - FR-B01: ผู้ใช้งานสามารถเข้าสู่ระบบด้วยอีเมลและรหัสผ่านได้
   - FR-B02: ระบบต้องตรวจสอบบทบาทและนำทางไปยังพอร์ทัลของผู้ใช้งานแต่ละกลุ่มโดยอัตโนมัติ
   - FR-B03: ผู้ใช้งานสามารถออกจากระบบ (Sign Out) และปิดเซสชันได้อย่างปลอดภัย
   - FR-B04: ผู้ใช้งานสามารถดูและแก้ไขข้อมูลส่วนตัวพื้นฐานได้

3. **ความต้องการสำหรับผู้เช่า (Rental - FR-R)**:
   - FR-R01: ผู้เช่าสามารถเข้าดูแดชบอร์ดส่วนตัว แสดงข้อมูลห้องพัก ชั้น และสถานะสัญญาเช่าได้
   - FR-R02: ผู้เช่าสามารถตรวจสอบใบแจ้งหนี้ประจำเดือน รายละเอียดค่าห้อง ค่าน้ำ ค่าไฟ ค่าส่วนกลาง และวันครบกำหนดชำระได้
   - FR-R03: ผู้เช่าสามารถสร้างและแสดง QR Code PromptPay ที่มียอดเงินตรงตามยอดบิลเพื่อสแกนชำระเงินได้
   - FR-R04: ผู้เช่าสามารถอัปโหลดไฟล์ภาพสลิปหลักฐานการโอนเงิน ระบุยอดเงินและวันเวลาที่โอนเข้าสู่ระบบได้
   - FR-R05: ผู้เช่าสามารถตรวจสอบประวัติการชำระเงินย้อนหลัง และดาวน์โหลดใบแจ้งหนี้/ใบเสร็จเป็นเอกสาร PDF ได้
   - FR-R06: ผู้เช่าสามารถส่งคำร้องแจ้งซ่อมแซมห้องพัก โดยระบุหัวข้อ รายละเอียด หมวดหมู่งานซ่อม ระดับความด่วน และแนบรูปภาพได้
   - FR-R07: ผู้เช่าสามารถติดตามสถานะการดำเนินงานของคำร้องแจ้งซ่อมและอ่านข้อความตอบกลับจากเจ้าหน้าที่ได้
   - FR-R08: ผู้เช่าสามารถอ่านประกาศ ข่าวสาร และมาตรการสำคัญของหอพักได้

4. **ความต้องการสำหรับเจ้าหน้าที่นิติบุคคล (Staff - FR-S)**:
   - FR-S01: เจ้าหน้าที่สามารถดูแดชบอร์ดนิติบุคคล แสดงยอดเงินรอตรวจสอบ งานแจ้งซ่อมคงค้าง และอัตราห้องว่างได้
   - FR-S02: เจ้าหน้าที่สามารถจัดการผังห้องพัก (Room Grid) ตรวจสอบและเปลี่ยนสถานะห้อง (ว่าง, มีผู้เช่า, ซ่อมแซม) ได้
   - FR-S03: เจ้าหน้าที่สามารถจัดการทะเบียนผู้เช่า บันทึกข้อมูลสัญญาเช่า วันที่เข้าพัก-ย้ายออก และเงินประกันได้
   - FR-S04: เจ้าหน้าที่สามารถบันทึกเลขมิเตอร์น้ำและมิเตอร์ไฟประจำเดือน โดยระบบจะแสดงเลขเดิมและคำนวณหน่วยใช้อัตโนมัติ
   - FR-S05: เจ้าหน้าที่สามารถสร้างและออกบิลประจำเดือนให้แต่ละห้องพักพร้อมกันหรือแยกรายห้องได้
   - FR-S06: เจ้าหน้าที่สามารถตรวจสอบภาพสลิปการโอนเงิน เปรียบเทียบกับยอดบิล และกดอนุมัติหรือปฏิเสธพร้อมระบุเหตุผลได้
   - FR-S07: เจ้าหน้าที่สามารถจัดการคำร้องแจ้งซ่อม มอบหมายช่าง อัปเดตสถานะงาน และบันทึกหมายเหตุการซ่อมได้
   - FR-S08: เจ้าหน้าที่สามารถสร้าง แก้ไข ลบ และปักหมุดประกาศข่าวสารสำคัญได้
   - FR-S09: เจ้าหน้าที่สามารถปรับแต่งเนื้อหา ข้อความ รูปภาพบนหน้าแรกของเว็บไซต์ผ่านระบบ CMS ได้
   - FR-S10: เจ้าหน้าที่สามารถรีเซ็ตรหัสผ่านชั่วคราวให้แก่ผู้เช่ากรณีผู้เช่าลืมรหัสผ่านได้

5. **ความต้องการพิเศษสำหรับเจ้าของหอพัก (Owner - FR-O)**:
   - FR-O01: เจ้าของสามารถใช้งานฟังก์ชันของเจ้าหน้าที่นิติบุคคล (Staff) ได้ทุกฟังก์ชันโดยอัตโนมัติ
   - FR-O02: เจ้าของสามารถดูแดชบอร์ดวิเคราะห์การเงินขั้นสูง สรุปยอดรายได้รวม ยอดค้างชำระ และอัตราการจัดเก็บเงินได้
   - FR-O03: เจ้าของสามารถดูสถิติอัตราการเข้าพัก (Occupancy Rate) และการกระจายตัวของผู้เช่าแยกตามประเภทห้องและชั้นได้
   - FR-O04: เจ้าของสามารถสร้าง แก้ไข ลบ ข้อมูลประเภทห้องพัก (Master Data: อัตราค่าเช่า, ค่าน้ำต่อหน่วย, ค่าไฟต่อหน่วย) ได้
   - FR-O05: เจ้าของสามารถสร้าง แก้ไข และระงับบัญชีผู้ใช้งานของเจ้าหน้าที่นิติบุคคลได้
   - FR-O06: เจ้าของสามารถตรวจสอบประวัติการทำธุรกรรมและการดำเนินงานที่สำคัญของระบบ (Audit Logs) ได้

### 3.1.3 ความต้องการที่ไม่ใช่เชิงหน้าที่ (Non-Functional Requirements)
1. **ด้านความมั่นคงปลอดภัย (Security)**:
   - รหัสผ่านของผู้ใช้งานต้องถูกเข้ารหัสอย่างปลอดภัย (Hashed Password)
   - มีระบบตรวจสอบสิทธิ์ระดับแถวข้อมูล (Row Level Security: RLS) บนฐานข้อมูล PostgreSQL
   - บังคับใช้ HTTPS สำหรับการรับส่งข้อมูลทั้งหมด
   - ป้องกันการเข้าถึงหน้าเว็บข้ามบทบาทผ่าน Middleware Authorization
2. **ด้านประสิทธิภาพและความเร็ว (Performance)**:
   - เวลาในการโหลดหน้าเว็บครั้งแรก (First Contentful Paint) ไม่เกิน 2.0 วินาที
   - การประมวลผลการคำนวณมิเตอร์และสร้างบิลใช้เวลาไม่เกิน 1.0 วินาที
   - ฐานข้อมูลมีการทำดัชนี (Indexing) บนฟิลด์ที่ใช้ค้นหาและกรองข้อมูลบ่อยครั้ง
3. **ด้านความพร้อมใช้งานและการรองรับอุปกรณ์ (Availability & Usability)**:
   - ระบบทำงานผ่านเครือข่ายอินเทอร์เน็ตได้ตลอด 24 ชั่วโมง (High Availability)
   - หน้าจอออกแบบตามหลัก Responsive Web Design แสดงผลได้อย่างสมบูรณ์แบบบนคอมพิวเตอร์ แท็บเล็ต และสมาร์ตโฟน
   - ส่วนติดต่อผู้ใช้มีรูปแบบมินิมอลพรีเมียม ตัวหนังสือคมชัด สีสันสบายตา ปราศจากอิโมจิที่ทำให้ดูไม่เป็นทางการ
4. **ด้านความถูกต้องของข้อมูล (Data Integrity)**:
   - มีข้อกำหนดทางธุรกิจ (Business Rules) บังคับ 1 บัญชีผู้เช่า ต่อ 1 ห้องพักเท่านั้น (`room_id` เป็น UNIQUE)
   - ระบบไม่มีการตัดเงินอัตโนมัติ ต้องมีกระบวนการแนบสลิปและตรวจสอบโดยเจ้าหน้าที่เสมอ

## 3.2 การวิเคราะห์และออกแบบระบบเชิงฟังก์ชันด้วยแผนภาพ UML

### 3.2.1 แบบจำลองการใช้งานระบบ (Use Case Diagram)
ระบบแบ่งกลุ่มผู้ใช้งานออกเป็น 4 บทบาท โดยมีสถาปัตยกรรมการสืบทอดสิทธิ์ (Inheritance) คือ ผู้เช่า (Rental) และนิติบุคคล (Staff) สืบทอดสิทธิ์พื้นฐานจากผู้ใช้งานทั่วไป (BaseUser) ในขณะที่เจ้าของหอพัก (Owner) สืบทอดสิทธิ์ทั้งหมดของนิติบุคคล (Staff) และมีฟังก์ชันเฉพาะทางเพิ่มขึ้น ดังแสดงโครงสร้างความสัมพันธ์ในภาพที่ 3-1

```
+---------------------------------------------------------------------------------------------------+
|                     ระบบบริหารจัดการหอพักและอพาร์ตเมนต์ เดอะ สราญรมย์ เรสซิเดนซ์                         |
+---------------------------------------------------------------------------------------------------+

     [Visitor]
         |
         +-----> (UC-01: ดูข้อมูลหอพักและประเภทห้องพักหน้าแรก)
         +-----> (UC-02: ดูข้อมูลสิ่งอำนวยความสะดวกและการติดต่อ)

    [BaseUser]
         |
         +-----> (UC-03: เข้าสู่ระบบ / ออกจากระบบ / เปลี่ยนรหัสผ่าน)
```

```
+-----------------------------------------------------------------------------------+

|                                                                                   |
```

### 3.4.2 นโยบายความปลอดภัยและการตรวจสอบสิทธิ์
1. **การตรวจสอบสิทธิ์ผ่าน Middleware (`middleware.ts`)**: ทุกคำขอ (Request) ที่เข้าถึงเส้นทาง `/rental/*` และ `/staff/*` จะถูกตรวจสอบ Session Token ในระดับ Edge Middleware หากพบว่าไม่มีเซสชัน ระบบจะเปลี่ยนเส้นทางไปยัง `/login` ทันที และหากผู้เช่าพยายามเข้าถึง `/staff` ระบบจะบล็อกการเข้าถึงโดยอัตโนมัติ
2. **การรักษาความปลอดภัยระดับแถวข้อมูล (Row Level Security: RLS)**: บนฐานข้อมูล PostgreSQL ได้กำหนดนโยบายความปลอดภัย เช่น:
   ```sql
   -- ตัวอย่างนโยบาย RLS สำหรับตาราง bill: ผู้เช่าดูได้เฉพาะห้องตนเอง นิติบุคคลดูได้ทุกห้อง
   CREATE POLICY "rental_select_own_bill" ON bill
     FOR SELECT USING (
       auth.uid() IN (SELECT auth_uid FROM users JOIN rental_profile ON users.id = rental_profile.user_id WHERE rental_profile.id = bill.rental_profile_id)
       OR
       EXISTS (SELECT 1 FROM users WHERE users.auth_uid = auth.uid() AND users.role = 'staff')
     );
   ```

## 3.6 แผนการพัฒนา การทดสอบ และการประเมินผลระบบ

### 3.6.1 ลำดับขั้นการพัฒนาระบบ (Implementation Steps)
1. **การสร้างฐานข้อมูลและ Seed Data**: รันสคริปต์ `dormitory_schema.sql` บน Supabase สร้าง 11 ตาราง ดัชนี Foreign Keys และข้อมูลทดสอบเริ่มต้นครบ 3 บทบาท
2. **การตั้งค่าโครงสร้างโปรเจกต์ Next.js**: กำหนดโครงสร้าง App Router ติดตั้งไลบรารี `@supabase/ssr`, `lucide-react`, `qrcode`, `puppeteer-core` และเขียน Supabase Client Helper
3. **การพัฒนาส่วนติดต่อผู้ใช้งานและ Logic**: พัฒนาหน้าจอตาม Sitemap ทีละโมดูล โดยเชื่อมต่อข้อมูลแบบ Server Actions และ Client Components
4. **การพัฒนาระบบสร้างเอกสารทางการ**: พัฒนาโมดูลพิมพ์บิลและใบเสร็จทางการผ่าน Puppeteer Core

### 3.6.2 แผนการทดสอบระบบ (System Testing Plan)
การทดสอบระบบดำเนินการตามกระบวนการทางวิศวกรรมซอฟต์แวร์ 3 ระดับ:
1. **การทดสอบระดับหน่วย (Unit Testing)**: ทดสอบฟังก์ชันคำนวณหน่วยมิเตอร์และยอดเงินรวม ค่าน้ำ-ค่าไฟว่าได้ผลลัพธ์ถูกต้องตรงตามสูตร
2. **การทดสอบความมั่นคงปลอดภัย (Security Testing)**: ทดสอบการเข้าถึง URL ข้ามสิทธิ์ และทดสอบการสกัดกั้นข้อมูลด้วย RLS
3. **การทดสอบระบบโดยรวมด้วยวิธีกล่องดำ (Black-Box Testing)**: ทดสอบการทำงานของฟังก์ชันตาม Use Case โดยกำหนดกรณีทดสอบ (Test Cases) ดังแสดงตัวอย่างในตารางที่ 3-16
